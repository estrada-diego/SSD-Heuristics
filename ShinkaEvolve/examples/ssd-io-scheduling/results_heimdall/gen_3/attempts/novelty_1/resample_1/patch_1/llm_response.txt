<DESCRIPTION>
The current heuristic uses fixed thresholds (latency > 200, queue_len > 8, etc.) which may not adapt well to varying workload conditions. I'm proposing to make the latency threshold adaptive based on recent historical context.

The key insight is that what constitutes "high latency" depends on the recent baseline. If the system has been running with consistently low latencies (say, prev_latency_avg = 50µs), then even a current latency of 120µs might indicate a problem. Conversely, if the system has been under sustained load with prev_latency_avg = 180µs, then a current latency of 220µs might be more tolerable.

This adaptive approach should reduce false admits by catching latency spikes earlier when the system is normally fast, while avoiding excessive false rejects when the system is under sustained but manageable load.

I'm also adding a multiplicative factor that considers the interaction between current conditions and trends - if both current latency and queue length are elevated relative to recent history, we become more aggressive in rejection.

    Args:

        + features["prev_queue_len_3"]
    ) / 3.0

    if latency > 200.0:
        return 1

    if queue_len > 8:
        return 1

    if prev_latency_avg > 150.0:

def predict(features: Dict[str, float]) -> int:
    """
    Heuristic for SSD I/O admission control.

    Args:
        features: dict mapping feature name -> float value.
                  Keys: size, queue_len, prev_queue_len_1/2/3,
                        prev_latency_1/2/3, prev_throughput_1/2/3, latency.

    Returns:
        1  →  REJECT  (predicted slow/high-latency I/O — block or hedge)
        0  →  KEEP    (predicted fast/normal I/O — let through)

    Fitness being maximised:
        combined_score = 0.7 * weighted_f1 + 0.3 * (1 - false_admit_rate)

    False admits (predicting KEEP for a truly slow I/O) are the most costly
    error because they cause direct tail-latency spikes at the SSD.
    False rejects (predicting REJECT for a fast I/O) are less costly.
    """
    latency   = features["latency"]
    queue_len = features["queue_len"]
    size      = features["size"]

    prev_latency_avg = (
        features["prev_latency_1"]
        + features["prev_latency_2"]
        + features["prev_latency_3"]
    ) / 3.0

    prev_queue_avg = (
        features["prev_queue_len_1"]
        + features["prev_queue_len_2"]
        + features["prev_queue_len_3"]
    ) / 3.0

    # Adaptive latency threshold based on recent history
    base_latency_threshold = max(100.0, prev_latency_avg * 1.4)
    
    # Rule 1: adaptive latency spike detection
    if latency > base_latency_threshold:
        return 1

    # Rule 2: absolute high latency ceiling
    if latency > 250.0:
        return 1

    # Rule 3: queue congestion
    if queue_len > 8:
        return 1

    # Rule 4: sustained high latency trend
    if prev_latency_avg > 150.0:
        return 1

    # Rule 5: large request into congested queue
    if size >= 65536 and queue_len > 2:
        return 1

    # Rule 6: compounding pressure with adaptive sensitivity
    if prev_queue_avg > 6 and prev_latency_avg > 100.0:
        return 1
    
    # Rule 7: relative latency jump with queue pressure
    latency_ratio = latency / max(prev_latency_avg, 20.0)
    if latency_ratio > 2.0 and queue_len > 3:
        return 1

    return 0
